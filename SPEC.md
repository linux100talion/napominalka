# Protocol. Спецификация

Версия 0.2, 2026-10-30. Черновик по итогам обсуждения в `protocol.txt`.

## 1. Назначение

Автономное Android-приложение, которое круглосуточно ведёт человека по
суточной цепочке обязательных шагов. В плановое время каждого шага оно задаёт
проверочный вопрос и не отступает, пока шаг не закрыт. Если шаг не удаётся
закрыть за 10 минут, приложение считает конфиг негодным, записывает причину
и останавливается. Автор правит конфиг и запускает снова.

Главный результат работы: лог прохождения и журнал блокеров, по которым
дорабатывается конфиг.

## 2. Термины

- **Цикл**: суточное окно, начинается в `day_start` и длится 24 часа.
- **Шаг**: цель с плановым временем, проверочным вопросом и деревом подсказок.
- **Проверочный вопрос**: вопрос «да/нет», с которого начинается шаг.
- **Дерево подсказок**: узлы, по которым идёт человек после ответа «нет».
- **Узел**: один экран дерева: вопрос, инструкция, ввод текста, выбор, конец.
- **Закрытие шага**: достижение узла `done` или ответ «да» без продолжения.
- **Блокер**: шаг, который не закрыт за 10 минут или дошёл до узла `fail`.
- **Остановка**: принудительное завершение работы с записью причины.
- **Процесс**: дерево узлов, которое человек запускает сам кнопкой, вне
  графика. Параллелен цепочке и не влияет на неё.

## 3. Платформа и ограничения

- Нативное приложение, Kotlin, Android.
- Полностью офлайн. Никаких сетевых запросов, Google Play Services, Firebase,
  аналитики, обновлений по сети. Разрешение INTERNET не запрашивается.
- Распространение APK-файлом, установка вручную.
- Минимальная версия Android: предварительно 8.0 (API 26). Уточняется.
- Одно устройство, один пользователь, один активный конфиг.

## 4. Конфиг

### 4.1. Файл

- Формат JSON, кодировка UTF-8.
- Автор правит файл любым текстовым редактором на телефоне.
- Файл выбирается один раз через системный выбор файла. Приложение сохраняет
  доступ к нему и перечитывает при каждом запуске.
- Рекомендуемое место: `Documents/Protocol/config.json`.
- При ошибке в конфиге приложение не запускается и показывает, в какой строке
  и какая ошибка. Полный пример: `config.example.json`.

### 4.2. Корень

| Поле          | Тип     | Обяз. | Описание |
|---------------|---------|-------|----------|
| `version`     | число   | да    | Версия формата. Сейчас `1`. |
| `day_start`   | "HH:MM" | да    | Начало суточного цикла. |
| `timeouts`    | объект  | нет   | Переопределение таймеров, см. 4.3. |
| `steps`       | массив  | да    | Шаги по порядку. Минимум один. |
| `processes`   | массив  | нет   | Ручные процессы, см. 4.7. |

### 4.3. Таймеры (`timeouts`)

| Поле           | Умолчание | Описание |
|----------------|-----------|----------|
| `repeat_sec`   | 60        | Период повтора сигнала. |
| `escalate_min` | 5         | Через сколько минут текст меняется на «забыл». |
| `close_min`    | 10        | Через сколько минут принудительная остановка. |

Все три поля необязательные, задаются глобально. Значения по умолчанию
соответствуют согласованному поведению.

### 4.4. Шаг (`steps[]`)

| Поле     | Тип     | Обяз. | Описание |
|----------|---------|-------|----------|
| `id`     | строка  | да    | Уникальный идентификатор, латиница, цифры, `_`. Идёт в лог. |
| `time`   | "HH:MM" | да    | Плановое время внутри цикла. |
| `check`  | строка  | да    | Проверочный вопрос. |
| `forgot` | строка  | да    | Текст после эскалации: «Ты забыл ...». |
| `on_yes` | строка  | нет   | Узел после «да». Если нет, шаг сразу закрыт. |
| `on_no`  | строка  | да    | Узел после «нет». Корень дерева подсказок. |
| `nodes`  | объект  | да*   | Узлы дерева, ключ = id узла. *Обязателен, если есть `on_no` или `on_yes`. |

Правила времени: `time` трактуется внутри окна цикла. Если `time` меньше
`day_start`, шаг относится к следующим календарным суткам того же цикла.
Пример: `day_start` 07:00, шаг 02:00 наступает через 19 часов после начала
цикла. Шаги в списке должны идти в порядке неубывания времени внутри цикла.
Два шага с одинаковым временем допустимы, выполняются по порядку списка.

### 4.5. Узлы (`nodes`)

Общее поле `type`. Остальные зависят от типа.

| `type`        | Поля                         | Поведение |
|---------------|------------------------------|-----------|
| `yesno`       | `text`, `yes`, `no`          | Вопрос, две кнопки. Переход по ответу. |
| `instruction` | `text`, `next`               | Инструкция, кнопка «Понял». |
| `text`        | `text`, `next`               | Вопрос со свободным вводом. Пустой ответ не принимается. |
| `choice`      | `text`, `options[]`          | Выбор одного варианта. `options[]` = `{ "label", "next" }`. |
| `wait`        | `text`, `button`, `next`     | Только в процессах. Пауза без напоминаний, тихое уведомление с кнопкой `button`. Продолжение по нажатию. |
| `done`        | нет                          | Шаг или процесс закрыт. |
| `fail`        | `text`                       | Тупик. В шаге: остановка программы, см. 5.5. В процессе: завершение процесса, см. 5.8. |

Все `yes`, `no`, `next`, `options[].next`, `on_yes`, `on_no` указывают на
существующий ключ в `nodes` того же шага. Узлы разных шагов изолированы.

### 4.7. Процессы (`processes[]`)

| Поле     | Тип    | Обяз. | Описание |
|----------|--------|-------|----------|
| `id`     | строка | да    | Уникальный идентификатор среди процессов. Идёт в лог. |
| `title`  | строка | да    | Название кнопки на главном экране. |
| `start`  | строка | да    | Стартовый узел. |
| `nodes`  | объект | да    | Узлы, те же типы, что в 4.5, плюс `wait`. |

У процесса нет времени, `check` и `forgot`. Текст после эскалации в процессе:
«Ты не ответил: <текст текущего узла>».

### 4.6. Проверка конфига

Приложение отвергает конфиг, если:

- JSON не разбирается;
- `version` не поддерживается;
- `day_start` или `time` не в формате HH:MM;
- `steps` пуст или `id` шагов повторяются;
- порядок времён нарушен;
- ссылка на узел ведёт в никуда;
- узел недостижим от `on_yes` или `on_no` (предупреждение, не ошибка);
- в дереве есть цикл без выхода в `done` или `fail` (ошибка);
- узел `wait` встречается в шаге, а не в процессе;
- `id` процессов повторяются или `start` ведёт в никуда;
- у `text` или `check` пустая строка.

## 5. Поведение

### 5.1. Запуск

1. Пользователь открывает приложение и нажимает «Запустить».
2. Приложение читает и проверяет конфиг. При ошибке показывает её и стоит.
3. Определяет текущий цикл: последний `day_start`, который уже наступил.
4. Шаги текущего цикла, чьё время уже прошло, пишет в лог как
   `SKIPPED_RESTART`. Они в этом цикле не выполняются.
5. Ждёт ближайший шаг, чьё время ещё не наступило.
6. Запускает постоянный сервис с тихим уведомлением
   «Protocol работает. Следующий шаг: <id> в HH:MM».

### 5.2. Ожидание и наступление шага

- Между шагами приложение молчит.
- В плановое время шага, если предыдущий шаг закрыт, шаг **задаётся**.
- Если предыдущий шаг ещё не закрыт, новый шаг не задаётся и ждёт. Сразу после
  закрытия предыдущего все просроченные шаги задаются подряд, по порядку.
- Момент, когда шаг реально задан, фиксируется как `t0`. Все таймеры шага
  считаются от `t0`, не от планового времени.

### 5.3. Таймлайн шага

| Момент                 | Действие |
|------------------------|----------|
| `t0`                   | Полноэкранный вопрос `check` поверх блокировки, экран включается. Звук и вибрация. |
| каждые `repeat_sec`    | Повтор звука и вибрации, пока шаг не закрыт. |
| `t0 + escalate_min`    | Текст уведомления и экрана меняется на `forgot`. Вопрос остаётся тем же. |
| `t0 + close_min`       | Принудительная остановка, см. 5.5. Срабатывает в любом месте дерева. |

Повтор звука не подаётся, пока человек реально работает с экраном шага
(нажал кнопку меньше `repeat_sec` назад). Таймер остановки при этом идёт.

### 5.4. Ответы и дерево

- «Да» на `check`: если есть `on_yes`, переход в него, иначе шаг закрыт.
- «Нет» на `check`: переход в `on_no`.
- Дальше человек идёт по узлам. Каждый ответ пишется в лог с id узла.
- Узел `done`: шаг закрыт. Приложение проверяет просроченные шаги (5.2),
  иначе возвращается в ожидание.
- Узел `fail`: показывается его `text`, затем остановка (5.5).

### 5.5. Принудительная остановка

Причины: истёк `close_min`, или достигнут узел `fail`.

1. Текущий экран заменяется экраном «Шаг <id> не решён. Почему?» со свободным
   вводом. Пустой ответ не принимается. Таймера у этого экрана нет.
2. В журнал блокеров пишется: время, цикл, шаг, причина остановки
   (`TIMEOUT` или `FAIL`), пройденный путь по узлам, текст ответа.
3. Показывается экран «Программа остановлена. Исправьте конфиг и запустите
   снова». Сервис завершается, уведомления снимаются.
4. Остановленное состояние сохраняется. После перезагрузки телефона приложение
   само не запускается, пока человек не нажмёт «Запустить».

Отказаться от остановки нельзя.

### 5.6. Смена цикла

В момент `day_start` начинается новый цикл с первого шага. Благодаря лимиту
`close_min` открытый шаг не может дожить до смены цикла.

### 5.7. Перезагрузка и смена времени

- После перезагрузки, если состояние «работает», сервис поднимается сам и
  ведёт себя как при запуске (5.1), включая `SKIPPED_RESTART`.
- При смене системного времени или часового пояса расписание пересчитывается.

### 5.8. Процессы

- Запуск: кнопка с `title` на главном экране. Пишется `PROC_START`.
- Ход по узлам как в шаге (5.4). Ответы пишутся `PROC_ANSWER`.
- Повторы и эскалация действуют как в шаге, от момента показа текущего
  узла. Узел `wait` исключён: в нём напоминаний нет, ждать можно сколько
  угодно, висит тихое уведомление с кнопкой `button`.
- По истечении `close_min` на одном узле или при узле `fail`: экран
  «Процесс <id> не завершён. Почему?», запись в журнал блокеров с пометкой
  `PROC`, событие `PROC_FAILED`. Программа и основная цепочка продолжают
  работать.
- Узел `done`: событие `PROC_DONE`.
- Приоритет у графика. Если наступил шаг цепочки, экран шага выходит вперёд,
  таймеры процесса ставятся на паузу. После закрытия шага процесс
  возвращается на тот же узел.
- Несколько процессов могут идти одновременно. Главный экран показывает
  открытые процессы с текущим узлом; нажатие возвращает в процесс.
- Открытые процессы переживают перезагрузку телефона и остановку программы
  (5.5): они не зависят от состояния цепочки.

## 6. Интерфейс

### 6.1. Главный экран

- Состояние: «Работает», «Остановлена», «Конфиг не выбран», «Ошибка конфига».
- Текущий или следующий шаг и его время.
- Кнопки: «Запустить» / «Остановить вручную», «Выбрать конфиг»,
  «Проверить конфиг», «Логи».
- Блок «Процессы»: кнопка на каждый процесс из конфига, ниже список
  открытых процессов с текущим узлом.
- Ручная остановка пишется в лог как `MANUAL_STOP`, причина не спрашивается.

### 6.2. Экран шага

- Открывается поверх экрана блокировки, включает экран.
- Крупный текст вопроса, крупные кнопки. Для `text` поле ввода и «Ответить».
- Кнопка «Назад» не работает. Свернуть нельзя: при уходе с экрана он снова
  открывается на следующем повторе сигнала.
- Уведомление шага нельзя смахнуть. Кнопки «да» и «нет» для `check`
  дублируются в уведомлении.

### 6.3. Экран остановки

Описан в 5.5. Из него единственный выход: ввести причину.

### 6.4. Экран логов

Список файлов логов по датам, просмотр, кнопка «Поделиться файлом» через
системное меню (сохранить, отправить по Bluetooth и т.п.). Сетевых
действий приложение не совершает.

## 7. Хранение и лог

### 7.1. Файлы

Папка `Documents/Protocol/`:

- `logs/YYYY-MM-DD.log`: лог цикла, имя по дате начала цикла;
- `blockers.log`: журнал блокеров, дописывается;
- `config.json`: конфиг автора (приложение его не меняет).

### 7.2. Формат строки лога

Одна строка = одно событие. Поля через ` | `. Время локальное.

```
2026-10-30 09:00:00 | STEP_ASKED      | find_number |
2026-10-30 09:01:00 | REPEAT          | find_number | 1
2026-10-30 09:05:00 | ESCALATED       | find_number |
2026-10-30 09:06:12 | ANSWER          | find_number | check | no
2026-10-30 09:06:40 | ANSWER          | find_number | s1 | no
2026-10-30 09:07:05 | ANSWER          | find_number | s2 | yes
2026-10-30 09:07:05 | STEP_DONE       | find_number | 7m05s | repeats=6
```

События: `START`, `CONFIG_OK`, `CONFIG_ERROR`, `CYCLE_START`, `STEP_ASKED`,
`REPEAT`, `ESCALATED`, `ANSWER`, `STEP_DONE`, `SKIPPED_RESTART`, `FAIL`,
`TIMEOUT`, `BLOCKER_REASON`, `STOPPED`, `MANUAL_STOP`, `BOOT`, `TIME_CHANGED`,
`PROC_START`, `PROC_ANSWER`, `PROC_WAIT`, `PROC_RESUME`, `PROC_DONE`,
`PROC_FAILED`.

Для `ANSWER` в поле ответа для `text` пишется введённый текст, для `choice`
выбранный `label`.

### 7.3. Журнал блокеров

```
2026-10-30 09:10:00 | TIMEOUT | cycle=2026-10-30 | find_number | path=check:no>s1:no>s2:no>s3 | Х не берёт трубку
2026-10-30 14:22:00 | PROC TIMEOUT | cycle=2026-10-30 | power_off | path=p1:yes>p2:no>p2i | Чайник на даче, не дойти
```

### 7.4. База данных

Локальная SQLite (Room) с теми же событиями для экрана логов и будущей
статистики. Текстовые файлы первичны и пишутся всегда, база вторична.

## 8. Надёжность

- Постоянный foreground-сервис держит процесс живым.
- Плановое время шага ставится через AlarmManager как будильник
  (`setAlarmClock`), он не подавляется режимом Doze.
- Повторы внутри шага ведёт сервис, не будильники.
- Во время сигнала удерживается wakelock.
- Звук через аудиопоток будильника, чтобы работать при «Не беспокоить».
- Приёмник загрузки восстанавливает сервис после перезагрузки.
- Запрашивается исключение из оптимизации батареи.
- Инструкция по установке содержит шаги для прошивок с агрессивным убийством
  фона (Xiaomi, Huawei, Samsung): автозапуск, закрепление в недавних,
  отключение адаптивной батареи для приложения.

## 9. Разрешения

- Уведомления (Android 13+).
- Точные будильники (Android 12+).
- Полноэкранные уведомления (Android 14+).
- Foreground-сервис.
- Запуск при загрузке.
- Исключение из оптимизации батареи.
- Доступ к выбранному файлу конфига и папке `Documents/Protocol`.

Сеть не запрашивается.

## 10. Не входит в объём

- Редактор конфига внутри приложения.
- Несколько устройств, синхронизация, сбор ответов на сервер.
- Статистика и графики. Данные для них есть в логе.
- Несколько конфигов одновременно.

## 11. Открытые вопросы

1. Версия Android целевого устройства.
2. Где собирать APK: здесь в proot или на отдельном компьютере.
3. Нужно ли при «да» с `on_yes` считать шаг закрытым сразу или только после
   прохождения инструкций. Сейчас: после прохождения, до узла `done`.
